# 企业微信 Webhook 基础设施设计

## 目标

在现有京东订单采集流程后增加一个安全、可扩展的消息处理入口，并提供企业微信群机器人 Webhook 的基础发送能力。

本阶段只建立基础设施，不设计推送池的数据结构、消息生成规则、筛选规则、去重规则或自动发送流程。订单池成功更新后，程序会调用消息处理入口；当前处理器不产生消息，因此不会生成推送池，也不会向企业微信发送订单信息。

## 范围

本阶段包含：

- 从本机私有文件读取企业微信群机器人 Webhook 地址。
- 提供独立的 Webhook 测试消息命令。
- 在订单池成功更新后自动调用消息处理入口。
- 提供一个当前不产生消息的占位处理器。
- 使用只追加的 JSONL 日志记录处理过程和 Webhook 测试结果。
- 为上述行为增加自动化测试和使用说明。

本阶段不包含：

- 推送池文件及其数据结构。
- 订单内容到企业微信消息的转换逻辑。
- 订单筛选、状态判断、去重、覆盖或版本保留规则。
- 订单消息的自动推送、失败重试或补发。
- 把完整订单内容写入处理日志。

## 现有流程

当前 `capture` 命令依次执行：

1. 采集京东订单原始响应并追加到原始日志。
2. 从完整原始日志重建订单池。
3. 输出采集页数、响应数和订单池订单数。

独立的 `pool` 命令只负责重建订单池。本阶段不改变原始采集和订单池的数据格式。

## 设计

### Webhook 配置

默认从 `data/wechat_webhook.txt` 读取企业微信群机器人 Webhook URL。文件内容为一行完整 URL，读取时忽略首尾空白。

Webhook URL 属于密钥：

- 配置文件只保存在本机，并由现有的 `data/` 忽略规则排除在 Git 之外。
- 程序输出、异常信息和日志不得包含完整 URL。
- 配置错误只使用安全的概括性说明，例如“Webhook 配置为空”或“Webhook 地址格式不正确”。

### Webhook 发送器

发送器只负责把已经形成的企业微信消息提交给群机器人，不负责读取订单池、生成消息或管理队列。

本阶段发送器用于测试消息命令。它应当：

- 使用企业微信群机器人支持的消息格式发送固定测试文字。
- 同时校验 HTTP 状态和企业微信响应中的业务状态。
- 将网络异常、非成功 HTTP 响应、无效 JSON 响应和企业微信业务错误统一转换为安全的应用错误。
- 不在错误对象、终端输出或日志中暴露 Webhook URL。

### 测试消息命令

新增 `wechat-test` 命令，默认读取 `data/wechat_webhook.txt`，并允许显式指定另一个本机配置文件。

命令发送一条固定、无订单信息的测试消息。成功时返回成功退出码并显示简短确认；失败时返回失败退出码并显示不含密钥的概括性提示。

测试命令的用途只是验证配置、网络和企业微信机器人是否可用，不代表订单消息自动推送已经启用。

### 消息处理入口

增加一个独立的处理器边界，由订单池更新流程调用。处理器与采集器、订单池构建器和 Webhook 发送器分离。

当前占位处理器接收订单池更新结果或订单池路径，执行后明确返回“无消息”。它不判断订单状态、不筛选订单、不建立推送池，也不调用 Webhook。

这个边界为后续功能预留以下能力，但本阶段不定义其具体数据模型：

- 读取订单池中的全部订单。
- 根据未来规则生成或跳过推送内容。
- 将生成结果写入未来的推送池。
- 当未来推送池产生可发送消息时触发 Webhook。

### 流程接入

`capture` 命令的执行顺序调整为：

1. 完成所有分页采集。
2. 成功重建订单池。
3. 调用消息处理入口。
4. 输出采集和订单池结果。

采集失败时不重建订单池，也不运行处理器。订单池重建失败时不运行处理器。

独立的 `pool` 命令本阶段仍只负责重建订单池，不自动调用消息处理器，以免改变它作为手动修复工具的含义。未来若需要从重建后的订单池生成消息，应通过明确的新命令或新的已批准设计实现。

当前处理器不会产生消息，因此 `capture` 永远不会因为本阶段功能而自动发送企业微信订单信息。

## 日志

处理与 Webhook 测试事件追加写入 `data/push_processing.jsonl`。每行是一个独立 JSON 对象，至少包含：

- 事件发生时间。
- 事件类型。
- 结果状态。
- 必要的安全错误摘要。

本阶段需要记录的事件包括：

- 处理器开始运行。
- 处理器完成且没有产生消息。
- 处理器异常。
- Webhook 测试发送成功。
- Webhook 测试发送失败。

日志不得包含：

- Cookie。
- Webhook URL 或其中的密钥参数。
- 完整订单对象。
- 客户姓名、电话、地址等订单详情。

日志写入失败应作为明确错误报告，不能静默丢失审计信息。对于 `capture`，原始采集和订单池已成功完成的事实仍应在错误提示中说明。

## 错误处理

- Webhook 配置缺失、为空或格式错误：测试命令失败，不发起网络请求。
- Webhook 网络或业务错误：测试命令失败，记录安全摘要。
- 处理器错误：记录处理失败；`capture` 返回失败，并明确说明原始采集及订单池已经成功，只有后续处理失败。
- 日志错误：相关命令返回失败，不把敏感上下文打印到终端。

所有用户可见错误都应说明失败阶段，并给出可执行的检查方向，但不得回显敏感值。

## 测试

自动化测试至少覆盖：

- 正确读取带首尾空白的本机 Webhook 文件。
- 配置文件缺失、为空及 URL 格式错误。
- Webhook HTTP 成功且企业微信业务成功。
- 非成功 HTTP 响应、无效 JSON、企业微信业务错误和网络异常。
- 所有错误输出与日志均不包含完整 Webhook URL。
- `wechat-test` 成功与失败时的退出码和安全提示。
- `capture` 在订单池成功后调用占位处理器。
- 采集失败或订单池失败时不调用处理器。
- 占位处理器返回无消息时不调用 Webhook，也不创建推送池。
- 处理器事件和 Webhook 测试事件正确追加到 JSONL 日志。
- 日志内容不包含订单详情或认证信息。

## 完成标准

- 用户可以将企业微信机器人地址保存在本机配置文件中，并通过独立命令发送固定测试消息。
- 正常采集完成后，占位处理器会自动运行并留下安全日志。
- 当前流程不会创建推送池，也不会自动推送任何订单信息。
- 代码边界允许未来在不修改采集与订单池格式的前提下，单独设计并加入消息计算、推送池和自动发送能力。
